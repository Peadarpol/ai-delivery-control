## Step 4 — Code fixes (two one-liners in init_session.py, same file, same commit)

### Fix 1 — HIB-FM8-02: harness_version reads from harness_version.txt

**File**: `.agent/scripts/init_session.py`
**Location**: Around line 251 (the `session_ledger.jsonl` write)
**Problem**: `harness_version` is hardcoded as `"2.0"` in every session ledger entry.
Forensic analysis of "which framework version was running?" is always wrong.

Find the line that writes `"harness_version": "2.0"` (or similar hardcoded string).
Replace with a dynamic read:

```python
# Read harness version dynamically
_version_file = Path(__file__).parent.parent.parent / "harness_version.txt"
_harness_version = _version_file.read_text(encoding="utf-8").strip() if _version_file.exists() else "unknown"
```

Then use `_harness_version` in the ledger write instead of the hardcoded string.

Confirm `harness_version.txt` exists at the framework root and contains `1.3.3`
(update it as part of this release — see Step 6).

### Fix 2 — HIB-FM8-01: severity casing in heartbeat

**File**: `.agent/scripts/init_session.py`
**Location**: The `--post-commit` heartbeat mode, where it writes a `commit_made` event
to `harness_events.jsonl`
**Problem**: The heartbeat writes `"severity": "info"` (lowercase). All other writers
use uppercase. `distill_dream.py` reads `evt.get("severity") == "critical"` — this
mismatch means the dream phase bypass trigger is deaf to critical events sourced
from `ai_review.py` (which correctly writes uppercase `"CRITICAL"`).

Find all `"severity": "info"` string literals in `init_session.py` and change to
`"severity": "INFO"`.

Also fix `distill_dream.py` — the severity casing bug affects the dream phase bypass
trigger in two places. The actual variable used is `e["severity"]` (not `evt.get(...)`),
and `max_severity` is compared directly. The cleanest fix is to normalise casing at
the point where events are read from the file (around line 277), rather than patching
each comparison individually:

Find the loop that reads events from `harness_events.jsonl`. It will look something like:
```python
for e in events:
    # uses e["severity"]
```

At the point each event `e` is read or appended to the working list, normalise the
severity field:
```python
e["severity"] = e.get("severity", "INFO").upper()
```

This means all downstream comparisons — `e["severity"] == "critical"`,
`max_severity == "critical"`, and any others at lines ~383–400 — will work correctly
without individual changes. After adding the normalisation, verify the comparisons
at those lines still read as `== "CRITICAL"` (uppercase) rather than lowercase —
if they already use lowercase, update them to uppercase for consistency with the
documented schema.

### 7a — src/scripts/review_context_universal.md: Gate Finding Output Format

Open `src/scripts/review_context_universal.md`. Find the existing `## Decision Block` section
(around line 146). This section instructs agents writing ADRs to use the decision
block. **Do not modify it.**

Add a new, separate section after the AT/FM vocabulary tables. Title it
`## Gate Finding Output Format`. Content:

```markdown
## Gate Finding Output Format

Every FAIL and qualifying WARN finding in the gate verdict must use the decision
block format. A finding that cannot be expressed in this format is a suspicion,
not a finding — return suspicions as questions to the developer, not as blocking
concerns.

Required format for each FAIL or WARN finding:

```
Finding:      [one sentence — what the code does, not what it should do]
Tradeoff:     AT[N] — this code chose [specific pole] which [consequence for this system]
Exposes:      FM[N] — this creates [specific named risk]; [file:line if determinable]
Remediation:  [specific change that addresses the FM without reverting the AT intent]
```

Rules:
- AT and FM codes must come from the vocabulary tables above. No invented codes.
- The Tradeoff line names a specific pole, not just the tradeoff category.
  Incorrect: "AT1 — consistency vs availability"
  Correct:   "AT1 — this code chose availability; the cache write precedes the database
              commit, so a crash between the two leaves the cache holding a value the
              database will never confirm"
- The Exposes line names a specific risk in this codebase, not the generic FM definition.
  FM10 and FM4 findings at FAIL severity must include file:line.
- The Remediation addresses the FM. "Delete this" is not a remediation.
- PASS_FAST and PASS verdicts do not require the decision block.
- WARN verdicts require the decision block when the concern touches FM4, FM9, FM10,
  or FM12. For other WARN concerns it is encouraged but not required.
```
