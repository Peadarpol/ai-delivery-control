# Loop Inventory

This file catalogues the feedback loops the harness implements or claims to implement,
and the current verification status of each. It exists to answer one question
systematically, rather than case-by-case: for a given loop, does a producer's claim
actually reach its consumer, and does that consumer's action actually close back into
future agent behavior — or does the loop only look closed?

**Origin**: This inventory grew out of `SPEC-loop-closure-verification.md` (T1-K-19),
which was itself motivated by a single case (HIB-080) of a claimed cross-component
relationship silently failing to hold. T1-K-19's Phase A/B tooling is general-purpose;
this inventory is the seed list that tooling should eventually be run against
comprehensively, the same role `wiring_consumers.yaml` plays for Phase B's four named
artifacts today, but at the scale of the whole harness.

**Methodology**: Every finding below is grounded in a direct read of the actual file
or script named — not inferred from documentation or memory. Where a loop has not yet
been directly inspected, it is marked `NOT YET INVESTIGATED` rather than assumed
healthy or assumed broken.

---

## Taxonomy

Six distinct loop shapes were identified. Each needs a different verification method —
collapsing them into one generic check is itself a likely source of false confidence.

| Type | Shape | Right verification tool |
|---|---|---|
| Spec-to-test | Gherkin scenario → test assertion | Phase A (T1-K-19, in progress) |
| Multi-consumer wiring | Shared state → named consumer code | Phase B (T1-K-19, in progress) |
| Session-to-session | Session close write → next session read | Partially covered (decisions_log retention); rest unaudited |
| Incident-to-prevention | HIB → eval registration → regression check | Unaudited, findings below |
| Self-improvement | Friction signal → proposal → adoption | Unaudited, findings below (includes one confirmed live break) |
| Gate feedback | FAIL verdict → correction → non-repeated failure | Unaudited |

**Status legend**: `VERIFIED-WORKING` (bidirectional wiring confirmed in code) ·
`VERIFIED-BROKEN` (a specific defect confirmed in code) · `PARTIAL` (some closure
confirmed, a specific gap also confirmed) · `UNVERIFIED` (no mechanical check found;
not yet proven broken or working) · `NOT YET INVESTIGATED`.

## LOOP-001: Self-Improvement / Dream Phase

**Status**: `VERIFIED-BROKEN` (fix drafted in `SPEC-loop-closure-verification.md` v1.4, pending sign-off)
**Type**: Self-improvement
**Producer**: `.agent/scripts/distill_dream.py` — writes proposal cards to `.agent/state/dream_proposals/*__open.md`
**Consumer**: `.agent/scripts/harness_health.py` — `report_dream_proposal_staleness()`

### Finding

`distill_dream.py`'s proposal-card template never writes a `Generated: YYYY-MM-DD`
field. `harness_health.py`'s staleness parser requires exactly that field
(`re.search(r"Generated:\s*(\d{4}-\d{2}-\d{2})", content)`) and silently `continue`s
past any card where it's absent. Confirmed by reading both the actual template output
and the actual regex — every proposal ever generated by the current code is invisible
to the staleness monitor.

Verified against the one existing open proposal
(`verification-before-completion__state_anomaly__open.md`, created 2026-06-22, 41 days
old at time of audit — past the 30-day warn threshold). It shows correctly in the raw
open-count but is skipped entirely by the staleness sweep.

This is the same species of bug as HIB-DREAM-03 (a threshold-logic condition that is
silently never satisfiable) recurring in the same subsystem, undetected until this
audit.

### Secondary findings in the same loop

- When a detected pattern isn't in `distill_dream.py`'s hardcoded
  `proposed_rules_catalog`, the generated rule text is generic boilerplate ("Ensure
  correct implementation practices regarding X and verify results carefully") — even a
  surfaced proposal may carry near-zero information.
- No mechanism marks a proposal "adopted" or applies its diff after human review —
  the loop has no closing step even when a human does act on it.

### Disposition

Fix scoped in `SPEC-loop-closure-verification.md` v1.4 (Scenarios 4h–4j): template
fix, one-time backfill of the existing proposal, and a producer-output-vs-consumer-parser
regression test. Explicitly scoped as a diagnosed single-instance fix, not a
generalized "producer output satisfies consumer parser" contract-test pattern — see
§8 of that spec.

## LOOP-002: Capability Calibration

**Status**: `VERIFIED-WORKING`
**Type**: Self-improvement (reviewer scoring)
**Producer**: `src/scripts/capability_calibration.py` — `update_calibration_rebuttal()`
**Consumer**: same file — `get_calibrated_weight()`

### Finding

Genuinely closed, bidirectional loop. Rebuttal outcomes update `tp`/`fp` counters and
a weight (clamped `[0.5, 1.5]`) per capability; `get_calibrated_weight()` reads it
back, gated by posture invariant-pinning and a config enable flag. This is the model
to copy for other loops.

### Caveat

This tunes a numeric *weight* per capability, not the review's actual textual rule
content. It does not touch `review_context_universal.md` / `review_context_project.md`.
See LOOP-010 below.

### Pressure Test — already exists, not hypothetical

`tests/integration/test_capability_calibration.py` (confirmed during the test-suite
integrity audit) already is this loop's pressure test: hand-computed weight
precision (`0.9` after one accepted rebuttal, `0.945` after a subsequent rejection,
verified via `pytest.approx`) and correct clamping at both the `0.5` floor and `1.5`
ceiling. No gap here — cite this file rather than design a new test.

## LOOP-004: Incident-to-Eval

**Status**: `PARTIAL`
**Type**: Incident-to-prevention
**Producer**: `.agent/evals/incident_to_eval.py` (interactive wizard) → `golden_dataset.yaml`
**Consumer**: `.agent/evals/regression_runner.py`

### Finding

`incident_to_eval.py` is an interactive wizard; nothing gates a HIB from being filed
without a corresponding golden-dataset entry. The whole loop depends on an agent
remembering to run it per `governance.md`'s Incident Post-Mortem Protocol — no
mechanical enforcement found.

### Confirmed discrepancy between documentation and code

`.agent/workflows/eval-pipeline.md`'s documented escalation trigger states: *"Empty
Dataset: If `--regression-only` returns 0 cases, escalate to human immediately (gate
is hollow)."* The actual code in `regression_runner.py`, on an empty dataset, prints a
warning and calls `sys.exit(0)` — a **success** exit code, not an escalation. Verified
by reading the function directly. Doc and code disagree on exactly the failure mode
this tool exists to catch.

### Schema match confirmed (cross-checked against an independent audit's claim)

`incident_to_eval.py` writes `{"entries": [{"id", "source", "description", "trigger",
"expected_outcome", "test_reference", "severity", "date_added", "added_by"}]}`;
`regression_runner.py` retrieves via `entry.get("test_reference", "")` in both
`verify_test_exists()` and `run_test()`. Verified directly against both files — the
schema itself is correctly matched end to end. This is the part of the loop that
genuinely works.

### New finding, surfaced while verifying the schema-match claim above

`run_test()` (the `--run` execution path, used when actually running referenced
tests rather than just checking they exist) invokes
`subprocess.run(["poetry", "run", "pytest", ref, ...])` — hardcoded `poetry run`.
This directly contradicts this project's own standing rule (verification commands
must be interpreter-relative, never `poetry run`), and means `--run` mode would fail
outright for any contributor not using poetry specifically — which `CONTRIBUTING.md`
treats as optional (*"pip install... or use your virtualenv / poetry env"*).
`--verify-only` mode (existence-checking only) is unaffected, since it never invokes
`run_test()`. A real, previously-uncaught fragility in the one execution mode of an
already-partially-broken loop.

### Recommendation

File as its own HIB (doc/code mismatch on an escalation trigger, plus the `poetry
run` fragility found alongside it) rather than folding into a future spec silently —
both are independently actionable.

### Pressure Test (how to verify this loop stays closed)

Invoke `incident_to_eval.py` with mocked stdin to create a dummy entry pointing at
an intentionally failing test function, then run `regression_runner.py --verify-only`
and separately `--run` (using `sys.executable -m pytest`, not `poetry run`, once the
fragility above is fixed), asserting each mode's exit code and that the specific
entry `id` appears in the failure output.

## LOOP-012: Co-Change Coupling Reconciliation

**Status**: `PARTIAL` — producer works, no automatic consumer
**Type**: Emergent-drift detection
**Producer**: `.agent/scripts/co_change_reconciler.py` → `.agent/state/co_change_reconciliation_report.md`
**Consumer**: none found

### Finding

The reconciler itself is substantive and correctly structured — it classifies
boundary-crossing co-changes against the CDR ledger (`coupling_decisions.yaml`) into
undeclared / escalated / tolerated / accepted / ambiguous buckets, with an
escalation check for sanctioned couplings that have gotten worse. But its output
report is not read anywhere: `harness_health.py` has no function surfacing it (all
of `report_ai_reviews`, `report_rebuttals`, `report_capability_calibration`,
`report_governance_audit`, `report_schema_hardening`, `report_dream_phase`,
`report_token_trends`, `report_unmerged_branches`, `report_dream_proposal_staleness`,
`report_state_file_sizes`, `report_backlog` were checked; none reference this
report). This is a manual-CLI-only loop, same unenforced shape as LOOP-004.

### Secondary finding — a repeated latent bug, not isolated to this file

`co_change_reconciler.py`'s `_find_project_root()` calls `subprocess.run(...)` but
the file never imports `subprocess` — confirmed by reading the full import list
(`argparse`, `datetime`, `os`, `sys`, `Path`, `yaml` only). The resulting `NameError`
is masked by a bare `except Exception: pass`, silently falling back to a
directory-walk path resolution. Harmless in practice today (the fallback still finds
the project root correctly in this repo layout), but it means the git-rooted
resolution path has never actually executed — and, per the next finding, this exact
pattern recurs in a second file, suggesting a shared template origin rather than one
isolated typo.

## LOOP-013: Wiki-Lint Documentation-Code Consistency Loop

**Status**: `VERIFIED-BROKEN` — this is the loop most directly relevant to the
reviewer-instruction-integrity question that motivated LOOP-010/011
**Type**: Spec-to-test / documentation consistency (a code-side analogue to Phase A)
**Producer**: `.agent/scripts/wiki_lint.py` → `.agent/state/wiki_lint_findings.md`
**Consumer**: intended to be a human reading the findings report; no automated consumer

### Finding

`wiki_lint.py`'s stated purpose (its own module docstring) includes checking for
"orphaned rules: rule IDs in `review_context.md` missing AST checks in
`architecture_checks.py`" — precisely the mechanism that would answer whether the
AI reviewer's documented rules are actually enforced. Both of its hardcoded target
paths are stale and do not exist:

- `CONTEXT_FILE = src/scripts/review_context.md` — **does not exist**. The actual
  files, confirmed by directory listing, are `review_context_universal.md` and
  `review_context_project.md` — this script predates that split and was never
  updated.
- `ARCH_CHECKS_FILE = .agent/skills/senior-architect/scripts/architecture_checks.py`
  — **does not exist**. Confirmed: `.agent/skills/` contains only `meta/`,
  `stack-packs/`, and `universal/` — no top-level `senior-architect/`. The real file
  lives at `.agent/skills/universal/senior-architect/scripts/architecture_checks.py`.

`run_orphaned_rules_check()`'s first line is `if not CONTEXT_FILE.exists() or not
ARCH_CHECKS_FILE.exists(): return findings` — both paths are wrong, so this check
has silently returned an empty list on every run since whichever refactor moved
these files. `run_staleness_check()` shares `CONTEXT_FILE` and is degraded the same
way — `review_context_*.md`'s content has never been scanned for stale identifiers
either, only `.agent/wiki/*.md` pages.

**Corroborated by the actual findings file**: `.agent/state/wiki_lint_findings.md`
currently reads `Total Issues: 0` with "No discrepancies or stale identifiers
detected in the knowledge base!" — the exact outward signature of a silently-broken
check reporting false confidence, given the substantial rule content that actually
exists in `review_context_universal.md`/`review_context_project.md`.

### Secondary finding — the same subprocess-import bug, again

`wiki_lint.py` contains **two** definitions of `_find_project_root()` (the second
shadows the first); the second calls `subprocess.run(...)` with `subprocess` never
imported anywhere in the file. Same masked-`NameError`-via-bare-except pattern as
LOOP-012. Two independent files sharing an identical, specific bug shape is worth
treating as a template/copy-paste-origin issue, not two coincidences.

### Recommendation

This is a strong candidate for its own immediate fix, same treatment as LOOP-001 and
the regression-runner discrepancy — not folded silently into a future phase. It
directly answers part of the original LOOP-010 question ("is there already a
mechanism checking that reviewer rules are real") with: yes, one was built, and it's
been silently dead for some time.

## LOOP-014: Wiki Compilation Pipeline

**Status**: `VERIFIED-BROKEN` — dormant, not merely path-stale like LOOP-013
**Type**: Self-improvement / documentation-generation (feeds LOOP-013's factual-drift-check)
**Producer**: `.agent/scripts/wiki_compile.py` → `.agent/wiki/*.md`
**Consumer**: `wiki_lint.py`'s `run_factual_drift_check()` and the `WIKI_DIR` half of `run_staleness_check()`

### Finding

Three independent, compounding issues, each confirmed directly:

1. **No config to compile from.** `wiki_compile.py`'s `DOMAIN_REGISTRY` is built from
   `get_harness_config("wiki_domains", ...)`. This repo's `.agent/config.yaml` (read
   directly) has no `wiki_domains:` key at all — confirmed by the file's actual
   content, which only declares `model_routing`, `project`, `framework`,
   `architecture.layers`, `skip_paths`, and `review`. Per `harness_utils.py`'s
   `DEFAULTS`, this falls back to `{}`. The registry is empty; nothing is ever
   compiled.
2. **Confirmed by the artifact itself.** `.agent/wiki/index.md` — which
   `wiki_compile.py` regenerates on every run regardless of whether anything changed
   — literally reads `Last compiled: never` / `Pages: 0 / 0 ready`.
3. **`wiki_lint.py`'s *separate*, hardcoded `DOMAIN_REGISTRY`** (used only for its
   factual-drift-check, independent of `wiki_compile.py`'s config-driven one) still
   lists twelve GymBase-specific domains (`branch_isolation`, `saas_architecture`,
   `pos_booking_payments`, `trainer_conflict_global_integrity`, etc.) sourced from
   `docs/decisions/adr/adr_NNN_*.md`. That directory does not exist in this repo at
   all — confirmed by directory listing. This registry was evidently copied
   wholesale from GymBase (the reference implementation this harness was extracted
   from, per project history) and never adapted for the harness's own repo.

Net effect: `run_factual_drift_check()` silently skips every domain on every run
(each fails its own `if not wiki_path.exists(): continue` check), independent of and
in addition to LOOP-013's `CONTEXT_FILE`/`ARCH_CHECKS_FILE` path bugs. The one file
present in `.agent/wiki/` — `clean_architecture.md` — is orphaned leftover content
that neither current mechanism would regenerate; it does not reflect live state.

### Fourth, deeper finding — even the review-injection consumer path is separately broken

Discovered while cross-referencing an independent audit (see "Cross-Referenced
Findings" section below). `src/scripts/ai_review.py` does contain
`from wiki_compile import DOMAIN_REGISTRY` exactly as `wiki_compile.py`'s own
docstring claims — but that imported value is never referenced again anywhere else
in the 101KB file. It is dead code. The actual wiki-injection path runs through a
completely different route: `ai_review.get_adr_context()` delegates to
`context_loader.get_adr_context()`, which reads `.agent/wiki/{domain}.md` files
directly, gated by a **separate** `DOMAIN_REGISTRY` that `context_loader.py` imports
from `architecture_checks`:
```python
try:
    from architecture_checks import DOMAIN_REGISTRY
except ImportError:
    DOMAIN_REGISTRY = set()
```
`architecture_checks.py` was read in full — **it defines no `DOMAIN_REGISTRY` at
all.** This import always fails, always falls back to an empty set, and
`get_adr_context()`'s domain-membership check (`if domain not in DOMAIN_REGISTRY:
continue`) skips every domain, unconditionally. Wiki content is structurally
guaranteed to never reach a review prompt in this repo — independent of, and deeper
than, the config/registry problems above. Even a full fix of items 1–3 would not
close this loop without also fixing this import.

### Secondary finding — the same subprocess bug, a third time

`wiki_compile.py`'s `load_domain_registry()` contains a nested `_find_project_root()`
calling `subprocess.run()` with `subprocess` never imported anywhere in the file
(confirmed against the full import list: `argparse`, `hashlib`, `json`, `os`, `sys`,
`Path`, `harness_utils`, `httpx`, `yaml`). Same masked-`NameError`-via-bare-except
shape as LOOP-012 and LOOP-013. **This is now three files with the identical bug**
(`co_change_reconciler.py`, `wiki_lint.py`, `wiki_compile.py`) — no longer a
"maybe worth a sweep later" item; a fourth instance would not be surprising.

### Recommendation

Distinguish this from LOOP-013 when scoping a fix: LOOP-013's paths are simply wrong
and correctable. This loop needs a decision, not just a correction — either populate
`wiki_domains:` in `.agent/config.yaml` with domains that actually apply to this
repo (the harness's own architecture, not GymBase's), or explicitly decide this
subsystem is out of scope for a tooling repo and document why, rather than leaving
it silently dormant with a stale registry pointing at another project's files.

## LOOP-015: Schema-Hardening Trend

**Status**: `NO PRODUCER FOUND` — a phantom loop, distinct in kind from the others above
**Type**: Health-metric loop
**Producer**: none found
**Consumer**: `harness_health.py` — `report_schema_hardening()`

### Finding

The consumer side is well-built: it reads `.agent/state/schema_hardening_trend.csv`,
computes a coverage percentage and trend direction, and — importantly — degrades
gracefully with `Status: DATA SOURCE MISSING` if the file is absent, rather than

(confirmed — `stat` on the exact path fails). Unlike LOOP-001/004/013/014, this
isn't a broken producer — no script anywhere in `.agent/scripts/` or `src/scripts/`
writes to this path at all. `enforce_hardened_schemas.py` (the closest-named script)
is a pass/fail pre-commit gate for direct `BaseModel` usage; it prints a verdict and
exits, but never writes a trend CSV. This loop was designed (the consumer exists,
the config/doc references exist) but its producer half appears to have never been
built, at least not in this repo.

### Recommendation

Lower priority than LOOP-013/014 — the consumer's graceful degradation means this
isn't currently misleading anyone (it correctly reports "missing," not "healthy").
Worth a decision on whether to build the producer or remove the dead consumer code,
but not urgent in the way a silently-false-positive loop is.

## LOOP-017: Session Ledger Retention

**Status**: `VERIFIED-WORKING`
**Type**: Session-to-session (retention/archival)
**Producer**: `.agent/scripts/init_session.py` — `infer_and_close_previous_session()` appends `ledger_entry` to `session_ledger.jsonl`
**Consumer**: `.agent/scripts/retention_cleanup.py` — `process_target()`

### Finding

Verified directly: `ledger_entry` writes a `"date": date_str` field formatted via
`dt.strftime("%Y-%m-%d %H:%M")`. `retention_cleanup.py`'s target definition for this
file specifies `"date_field": "date"`, and its `_parse_date()` helper accepts
exactly that `"%Y-%m-%d %H:%M"` format among its tried patterns. Field name and date
format both match end to end — genuinely working. Same-shaped retention logic also
covers `harness_events.jsonl` (`timestamp_utc`) and `.ai-review-log.jsonl`
(`timestamp`), not independently re-verified this pass.

### Pressure Test — genuine gap, no existing test found

Unlike LOOP-002 and LOOP-016, **no test file for `retention_cleanup.py` exists
anywhere in the repo** — confirmed absent across all 59 files checked during the
test-suite integrity audit (`tests/`, `tests/integration/`, `tests/e2e/`). This loop
is correctly wired *today*, verified by direct code read, but has zero regression
protection: if either side's date-field name or format ever drifts, nothing would
catch it automatically. Proposed test (not yet written): create a mock
`session_ledger.jsonl` with one entry dated today and one dated well past the
configured retention window, run `retention_cleanup.py`, and assert the resulting
file contains exactly the recent entry while the old one is moved to archive.

## Cross-Referenced Findings from an Independent Audit

A second, independent loop-closure pass was run separately (recorded in
`LOOP_INVENTORY_GEMINI.md`) — given the same brief but no access to this document,
to get genuine triangulation rather than agreement bias. Cross-referencing its seven
findings against this inventory and re-verifying each one directly produced a
consistent pattern worth naming explicitly, since it's useful calibration for
weighing any future report from the same source:

- **Verdicts (is this loop broken or working) were reliable in every case checked** —
  6 of 7 findings' broken/working classification held up under independent
  re-verification (Gate Rebuttal, Session Ledger Retention, Co-Change Reconciler,
  Spec Grade Card, and the wiki-compilation conclusion all confirmed correct).
- **Specific supporting citations were wrong in 2 of the 3 "broken" findings dug
  into** — both the wiki-compilation claim ("`ai_review.py` doesn't import
  `DOMAIN_REGISTRY`" — it does; the import is just dead code, and the real break is

## Candidate New Loops (not yet designed or spec'd)

### LOOP-010: AI-Reviewer Instruction Content Loop (proposed)

No loop currently exists feeding review accuracy back into
`review_context_universal.md` / `review_context_project.md`'s actual wording. But the
signal to build it on already exists: `report_capability_calibration()` already
computes `precision < 0.30` → CRITICAL/"DEGRADING" per capability from the same
rebuttal data LOOP-002 tracks — today that only prints a colored warning.

**Proposed design**: feed degrading-capability signals into the dream-phase pipeline
(`distill_dream.py`) as a new signal source alongside `harness_events.jsonl` and
`.ai-review-log.jsonl`, generating proposal cards that target `review_context_*.md`
wording specifically, distinct from `SKILL.md` proposals. Reuses two already-working
mechanisms (calibration's precision math, dream-phase's proposal-card format) rather
than inventing new machinery.

### LOOP-011: Static Architecture Checks Calibration Loop — RESOLVED (confirmed absent)

**Status**: `VERIFIED` — no calibration loop exists for this mechanism, confirmed by direct read

Read `architecture_checks.py`'s `main()` in full. Severity is derived from a static,
hardcoded `RULE_SEVERITY_MAP` dict (e.g. `LAYER_BOUNDARY: FAIL`, `HIGH_COUPLING: WARN`)
and passed through `posture.disposition()` — the same posture/baseline mechanism
HIB-080 fixed, confirmed correctly wired here post-fix (`baseline=baseline_data`,
`touched_files=touched_files` are both present and populated, not vacuous). But there
is no import of, or reference to, `capability_calibration.py` anywhere in this file.
`architecture_checks.py` runs as a fully separate pre-commit hook from `ai_review.py`
(confirmed in `pre-commit-config.yaml.template` — `architecture-checks` and
`ai-adversarial-review` are two distinct hook entries), and its rule taxonomy
(`LAYER_BOUNDARY`, `HIGH_COUPLING`, `BRANCH_FILTER`, etc.) is a different namespace
from calibration's `capability` keys entirely. **Confirmed finding, not a design
gap to leave open**: this is a structurally separate, statically-severity-mapped
checker with zero feedback loop. If LOOP-010's proposed reviewer-instruction loop is
built, it will need its own separate design for `architecture_checks.py` — it cannot
reuse `capability_calibration.py`'s existing wiring, because none exists to extend.

**A positive counter-example worth keeping**: this same file already fails loud on
an empty/misconfigured scan ("zero Python files were found across all layer
paths" → `sys.exit(1)`) rather than silently passing — exactly the discipline
missing from `regression_runner.py` (LOOP-004) before its fix. Worth citing as the
model pattern when the LOOP-004 fix is implemented.
