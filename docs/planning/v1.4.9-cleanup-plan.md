## 0. Resolved Design Decisions (pre-handoff)

1.  **D1 — T1-E-04 YAML strategy: hybrid fallback.** The shared loader uses `yaml.safe_load`
    when importable and falls back to **one** shared indentation-aware parser in `harness_utils`
    (extending the HIB-041 `validate_yaml_config` precedent in `bootstrap/migration_base.py`) —
    never N per-file copies. Do not vendor PyYAML. Consistent with the framework's degradation
    contracts: full correctness where the environment allows, one governed fallback where it
    doesn't. (Peter, 2026-07-08.)
2.  **D2 — T1-E-03 `schema_version`: add it.** `init_session.py` emits `schema_version: "1.0"`;
    all readers tolerate absence (treat missing as `"1.0"`). Rationale: T1-B-11 adds
    `session_kind` to session.json **in this same release** — the schema is evolving now, so
    versioning pays immediately; an exemption would be contradicted within the release.
    (Peter, 2026-07-08.)
3.  **D3 — SPEC-cdr-ledger-piece3: deferred out of v1.4.9, pending T1-G-18.** The
    enforcement-postures spec's `baseline.py` (human-only generation, tamper hash, HARD STOP
    class) will establish the harness's baseline-CLI pattern; building piece3 first risks two
    divergent baseline patterns. Revisit after the T1-G-18 placement decision — the roadmap
    (v1.4.8 deferred-items note) already flags exactly this question. The draft acceptance
    criteria in §3 below are retained as the seed for the eventual spec. (Peter, 2026-07-08.)
4.  **D4 — T1-B-11: layered "verifiable session governance", not guaranteed startup.**
    RESOLVED. Investigation concluded that for an unknown agent (dozens of variants, no common
    hook surface), **session start is not an enforceable boundary** — the only shared
    infrastructure every agent passes through is the filesystem (context files) and git. The
    item's goal is therefore renamed from "reliable startup" to **verifiable session
    governance**: the harness cannot force startup at t=0, but it can guarantee that ungoverned
    work is never mistaken for governed work — consistent with the framework's declared model
    (hard enforcement at the commit boundary, convention everywhere else). Four layers:
    *   **Layer 1 — session-control phrases (docs + shims, in scope).** Standardise
        **"Start Session"** and **"Close Session"** as recognised control phrases in `AGENTS.md`
        (echoed in the generated shims: CLAUDE.md, GEMINI.md, .cursorrules) that any agent must
        map to `init_session.py` and the close protocol. Uniform meaning across all agent
        variants.
    *   **Layer 2 — commit-boundary verification (in scope; replaces old AC3).** The pre-commit
        chain verifies a fresh session exists; disposition governed by three dials — see
        rewritten AC3 below.
    *   **Layer 3 — human entry point (docs only, in scope).** Document the recommended human
        practice: say "Start Session" at commencement and "Close Session" at end (getting-started
        + agent operations guide), noting Layer 2 backstops forgetting. A wrapper/launcher is
        explicitly **not built** — friction disproportionate to residual risk once Layers 1+2
        exist.
    *   **Layer 4 — MCP server (out of scope).** A harness MCP server exposing
        `session_start`/`session_status` as the cross-agent convergence bet (agents invoke tools
        more reliably than they obey prose). File as a separate strategic backlog candidate; not
        v1.4.9.
    **Consequence for scope:** T1-B-11 is fully **unblocked** — AC1, AC2, rewritten AC3
    (Layers 1+2, `--lite` init), and all AC4 tests are in Gemini's deliverable scope.
    (Peter, 2026-07-08.)

    Superseding note (2026-07-11). D4's four-layer design is revisited. Layer 2 (commit-boundary verification), the --lite init mode, and the anti-salami-slicing guard are deferred out of v1.4.9, pending T1-K-12's resolution — building a soft heuristic backstop before T1-K-12's hard-block mechanism is decided risks solving a problem T1-K-12 may make moot. Layer 1 (session-control phrases) and Layer 3 (documented human practice) are unaffected and remain in scope. T1-B-11's actual v1.4.9 delivery is narrowed to honest outcome labeling only — see the revised entry in §2 below. Layer 2 material is retained there as seed acceptance criteria for the follow-up ticket, not deleted. (Layer 4 — the MCP server — was already out of scope for v1.4.9 from the original D4 decision, for unrelated reasons; nothing new to retain there.)

    *   **Verdict:** Real gap (confirmed). `config.yaml` is parsed ~20 distinct ways across three
        incompatible strategies — hand-rolled flat regex, line/indentation parsers, and
        `yaml.safe_load` — with no shared loader and duplicated defaults.
    *   **Evidence:** Regex readers (`check_traceability.py:61,65`, `acceptance_check.py:62-100`,
        `acceptance_hook.py:64-74`, `pm_scaffold.py:48-60`, `check_spec.py:77-106`,
        `init_session.py:200-206`) grab the *first* `specs_path:`/`mode:` regardless of nesting;

    *   **Acceptance criteria:**

           PyYAML; no per-file copies.
        3. All per-file `load_config`/`get_specs_path`/`get_config_options` bodies become thin calls
           into the shared loader.
        4. **(folds in HIB-061)** `check_traceability.py` resolves `traceability.specs_path`
           (section-aware), falling back to `spec_gate.specs_path` then the default; `mode` is read
           from the `outer_loop:` block only.
        5. Regression test: a config where `spec_gate.specs_path != traceability.specs_path` and an
           unrelated `mode:` key exists above `outer_loop:` yields the correct per-role values.
    *   **Note:** `check_traceability.py`'s misread is currently *latent* — masked only because the
        harness's own `.agent/config.yaml` omits these keys and the template duplicates the value.
        Real for downstream configs that diverge.

## 2. Session-Lifecycle Reliability (non-frontier agents)

*   **[T1-B-11] Honest outcome labeling for non-code sessions** — **Priority: Medium** *(narrowed 2026-07-11 — see Superseding note in §0; commit-boundary verification deferred, see Part B below)*
    *   **Problem:** init_session.py's outcome inference assumes a session without commits reflects abandoned or incomplete work. Correct for coding sessions, wrong for analysis/planning/review sessions, which can complete real work and legitimately produce zero commits. Two concrete failure modes: a no-commit analysis/planning/review session is auto-labeled abandoned (init_session.py:243-247); an honest outcome_override: success with no commits is force-downgraded to partial (init_session.py:152-158,264-269) with no way to distinguish a legitimate no-commit success from a false claim.
    *   **Design:**
        1. Add session_kind (code|analysis|planning|review) to session.json, default "code" if unset. expects_commit is derived from session_kind (== "code"), never an independently-settable field — avoids two signals disagreeing.
        2. In infer_and_close_previous_session: no-commit + non-code kind + no override → label partial with a note, never silently abandoned. No-commit + non-code kind + outcome_override: success → accept the override as-is (no corroborating-artifact verification scheme — a heuristic "does a log entry look sufficiently detailed" check is itself spoofable and not worth the complexity). code kind (or default/unset) → existing HIB-053 downgrade behavior, completely unchanged.
        3. Tests: default-to-code regression; analysis-kind no-commit-no-override → partial not abandoned; analysis-kind no-commit + override success → accepted as success; code-kind no-commit + override success → still downgraded (regression, unchanged).
        4. Update docs/state-file-schema.md for the new session_kind field.
    *   **Deferred pending T1-K-12** — commit-boundary session verification, `--lite` init,
        anti-salami-slicing guard. Retained below as seed material for the follow-up ticket,
        not active v1.4.9 scope. Revisit once T1-K-12 determines whether agents retain any
        commit path this verification would meaningfully gate.

        > **Retained seed material (not active scope):**
        >
        > *(Rewritten per D4 — Layers 1+2)* Commit-boundary session verification + control phrases:
        > *   **(a) Session-control phrases.** `AGENTS.md` (and generated shims) declare
        >     "Start Session" / "Close Session" as recognised control phrases mapping to
        >     `init_session.py` and the close protocol. Getting-started + agent-operations docs
        >     recommend the human habit of saying them, noting the commit-boundary backstop.
        > *   **(b) `init_session.py --lite`.** Stamps session identity (session ID, ledger row,
        >     `session.json`) with **no context gathering** — near-zero cost remediation for
        >     trivial changes. Lite sessions are marked `init_mode: lite` in `session.json` and
        >     the ledger.
        > *   **(c) Pre-commit session verification** with three dials:
        >     *   *Applicability*: applies only to agent-authored commits (`AGENT_ID` env set —
        >         same convention family as existing agent-limit enforcement). Human/CI commits
        >         are exempt.
        >     *   *Disposition by change class*: reuse the existing diff classifier — docs-only /
        >         version-bump / whitespace class → blocked until **lite** init; anything touching
        >         code, tests, or config semantics → blocked until **full** init. Mixed diffs take
        >         the **stricter** class. Classification is deterministic (paths, extensions,
        >         size cap).
        >     *   *Freshness*: "session exists" means heartbeat-valid ACTIVE session, not any
        >         ACTIVE file — a stale/orphaned session does not satisfy the check (no permanent
        >         hall pass).
        > *   **(d) Anti-salami-slicing guard.** Every lite-init commit logs its change class to
        >     `harness_events.jsonl`; N consecutive lite-init commits (default 3) escalates the
        >     next commit to requiring full init. Dream phase sees the pattern.
        > *   **(e) Kind/class mismatch signal.** Where `session_kind` (AC1) disagrees with the
        >     observed change class (e.g. `session_kind: docs` committing code), the gate emits
        >     an advisory mismatch event — free signal, no new mechanism.
        >
        > Tests (seed, not active): (a) analysis, no commits, override success → stays
        > `success`; (b) code, no commits, override success → `partial` (unchanged); (c) killed
        > Cline session without startup → next `init_session` still records a coherent prior row.
        > Plus Layer-2 tests (new file or `tests/test_session_verification.py`): (d) agent commit,
        > no session, code diff → blocked, remediation message names full init; (e) agent commit,
        > no session, docs-only diff → blocked, remediation names `--lite`; (f) human commit
        > (no `AGENT_ID`), no session → passes; (g) mixed docs+code diff → treated as code class;
        > (h) stale-heartbeat ACTIVE session → treated as no session; (i) third consecutive
        > lite-init commit → escalates to full init; (j) `session_kind: docs` + code diff →
        > mismatch advisory event emitted.

    *   **Acceptance criteria (draft — promote to `docs/planning/specs/SPEC-cdr-ledger-piece3.md`):**

           `get_git_co_changes`, `architecture.layers` filter, and `boundary_of()` — must not
           reimplement crossing detection.
        2. Selects exactly the crossings the reconciler would classify "Undeclared" at the same
           thresholds (test: baseline pair-set == reconciler section-1 set on a fixture repo).
        3. Emits each as `scope: pair`, `status: tolerated`, `reason: unevaluated`, sorted files, with
           an `observed` snapshot (`co_changes`, `p_max`, `as_of`), and **no `rationale`** (constraint
           C3, `cdr_ledger_validate.py:120-122`).
        4. Idempotent/merge-safe: only add uncovered pairs, never overwrite human entries, continue
           `CDR-NNN` ids from the max existing; output passes `validate_ledger()` with zero errors.
        5. `--dry-run` (default) writes nothing; absent `architecture.layers` → graceful no-op exit.
        6. Test file `tests/test_co_change_baseline.py` using the existing temp-git-repo fixture pattern.

## 5. Governance Rule-Form Hardening (Match-the-Form audit) — IMPLEMENTED on-branch, pre-gate

**Provenance:** derived from auditing the `AGENTS.md` §4 H/S/C/G prohibition tables against the
"Match the Form to the Failure" method in the Superpowers skills framework
([obra/superpowers](https://github.com/obra/superpowers), `writing-skills`). Each item realigns a
rule's *form* (prohibition / positive recipe / structural slot / conditional) to its actual
failure type. **All four are implemented on `release/v1.4.9`; status is pre-gate, pending AI
review + human sign-off.**

*   **[MTF-1] H-04 selective-summary: prohibition → structural required slot** — **Priority: High**
    *   **Rationale:** "Omit findings…" is an *omission* failure; the binding form is a required
        template field, not a "never omit" prohibition. A missing/empty field is visible; a
        remembered-not-to-omit rule is not.
    *   **Change:** Added mandatory `### 2. Verification Findings (ALL severities)` slot to
        `.agent/skills/meta/context-compaction.md` (must state `None — verification ran clean`
        if empty); demoted `AGENTS.md` H-04 to a pointer; updated §6 step 3 and
        `.agent/skills/meta/validate.py` (now 6 required headings).

*   **[MTF-2] Prohibition-table header/form mismatch** — **Priority: Medium**
    *   **Rationale:** Header read "Never do this", but H-01/H-02/S-02 are positive recipes
        (correct form for their failure types) that the header contradicted — and it pressured
        future edits to force them into worse prohibition form.
    *   **Change:** Relabelled the column to `Rule` across all four tables and made each
        prohibition row self-contained (prefixed "Never" to H-03/05, S-01/03, C-01–04, G-01–04)
        so polarity no longer depends on the header.

*   **[MTF-3] H-06 / H-07 condition-led reframing** — **Priority: Low**
    *   **Rationale:** Both are conditionals keyed to an observable predicate (after a gate FAIL /
        after two same-class failures), phrased as bare prohibitions.
    *   **Change:** Rewrote both to lead with the condition and state the required action/artifact.

*   **[MTF-4] H-03 / H-05 rationalization + red-flags bulletproofing kit** — **Priority: High** (integrity — H-03 is the highest-stakes rule in the set)
    *   **Rationale:** Discipline failures (agent knows the rule, violates under pressure) need an
        explicit rationalization table + red-flags self-check; a bare one-line prohibition gets
        rationalized away.
    *   **Change:** Added `governance.md` §3.3 (kit for both rules) with pointers from the
        `AGENTS.md` H-03/H-05 rows. Rationalizations are grounded in the GymBase-distilled tactics
        recorded in §3.1 (weakened/commented assertions, `sys.exit(0)`, deleted tests, `--no-verify`
        /P-12), **not** verbatim transcripts.
    *   **Follow-up (RED-baseline enrichment):** extend the §3.3 tables with real verbatim
        rationalizations captured from pressure-scenario baseline runs or mined from the GymBase
        incident logs (the TDD-for-rules method). Treat §3.3 as the seed, not the ceiling. ✅ **DONE (commit 76283ca)**
