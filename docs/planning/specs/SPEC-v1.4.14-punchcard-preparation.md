- v1.10 (2026-07-30, Claude): Eighth adversarial review pass. **Architectural redesign**, not an additive patch — this round found that the `filter_diff_by_files(diff, target_files)` mechanism specified since v1.3 was fundamentally unworkable: it requires the full diff already materialized in Python memory before slicing can happen, which is exactly the unsafe operation the whole spec exists to avoid. Confirmed against the exact current code: `get_staged_diff()` is called unconditionally early in `_run_review()`, before the hard-ceiling checks even run (they need the materialized diff just to count lines/chars) — meaning the v1.9 "memory-safe pre-check" only protected the bypass-routing decision, not the pipeline the oversized diff is routed *into*. **Redesign (Option B — full unification)**: retire `filter_diff_by_files()` entirely. Replace it with a new `get_scoped_diff(target_files)` helper that fetches diff content directly from git via pathspec (`git diff --cached --unified=3 -- <file1> <file2> ...`), never materializing the full diff. This applies uniformly to both the existing Component 3 range (400–5,000 lines, `stratified`/`thin-standard`) and the new oversized (>5,000 lines) path — one mechanism, not two. `rebuttal.py` uses the same helper, fetching only the files recorded in the frozen gate-findings artifact, rather than calling `get_staged_diff()` at all. **Two prior fixes are retired as obsolete, not silently dropped**: (a) v1.8's "exact path-boundary matching" against the `diff --git a/<path> b/<path>` header — no longer applicable, since git's own pathspec resolution for literal paths is exact by default and there is no diff header to parse anymore; (b) v1.9's "quote-tolerant diff-git header matching" — same reason, no header parsing occurs. The `-z`/quote-safety fix for the `changed_files` *listing itself* (v1.9) is still required, since that list still feeds file selection before the scoped fetch. **Also adopted**: (2) a completely separate, previously-unaddressed bypass — the deprecated `.skip-ai-review` sentinel file check (verbatim in the code, unconditional, zero validation, distinct from `.skip-ai-reason.json`) — must be handled by the same oversized-diff pre-check routing, or removed outright given it's already marked deprecated by its own print statement. (3) `rebuttal.py`'s OOM exposure follows directly from the same root cause and the same fix. (4) `check_preflight_shortcut()`'s specific claimed vulnerability ("catastrophic regex backtracking") does not hold up — its whitespace/comment check uses plain `str.startswith()` on a tuple, not regex, and its one regex fallback is simple and non-catastrophic. However, a real, narrower issue remains: this function currently runs against the full diff before the hard-ceiling check, and once the full diff is never materialized for Component 3/oversized paths, its signature is structurally incompatible with that path — it must run against the scoped sub-diff instead. **Residual risk, not fully eliminated**: a single individually-enormous selected file (e.g. a 2GB blob flagged high-risk) could still risk OOM even via scoped pathspec fetching. Added a bounded/streaming read (`subprocess.Popen`, abort if output exceeds threshold) as defense-in-depth, narrowing but not eliminating this edge case.

- v1.12 (2026-07-30, Claude): Tenth adversarial review pass. All four findings confirmed. **Claim 1 (critical, self-correction)**: v1.11's "Size-first control flow" specified `git diff --cached --shortstat` as the size-determination mechanism, but `--shortstat` only reports line counts (`X files changed, Y insertions(+), Z deletions(-)`) — it is mathematically incapable of reporting character/byte size. A single-line, massively-oversized file (e.g. a minified bundle on one line) would read as "1 line" to the pre-check, incorrectly passing as "within hard ceiling", calling `get_staged_diff()`, and crashing the process with `MemoryError` before the downstream character-based sanity ceiling is ever reached. **Fix**: replace `--shortstat` with a streaming/bounded-read mechanism (e.g., `git diff --cached` piped or read in chunks, stopping and returning "oversized" the moment the hard-ceiling character bound is hit) to measure lines and chars simultaneously without buffering the full string. **Claim 2 (Integrity)**: `rebuttal.py` relies on `ai_review.py`'s `get_staged_diff()` because it needs to diff against the exact commit state that was reviewed. If `ai_review.py` now uses `get_scoped_diff()` and never materializes the full diff, `rebuttal.py` doing the same is sound for memory safety, but loses the guarantee that unreviewed files haven't been tampered with between the gate run and the rebuttal run. **Fix**: `ai_review.py` must compute its `_get_normalized_diff_hash()` using a full-commit mechanism that doesn't require diff text — specifically, `git write-tree` or equivalent index-state hash — so the artifact locks the *entire* commit state, and `rebuttal.py` must verify against this full-commit hash, not a hash of the sliced sub-diff. This anchors the rebuttal's contemporaneity to the full commit state, preventing tamper-leaks in unreviewed files. **Claim 3 (Empty-check decoupling)**: The current codebase uses `if not changed_files: return 0` to safely exit on genuinely empty commits. With v1.11, if this logic shares a code path with the new empty-slice guard (`get_scoped_diff()` returning empty), a genuinely empty commit would be incorrectly treated as a "sanity ceiling block" (Scenario 14). **Fix**: The genuinely-empty-commit check (`changed_files` is empty from git) must exit cleanly (`return 0`) *before* the empty-slice guard (where `changed_files` was non-empty but the *reviewed subset* resolved to no hunks) applies its block. **Claim 4**: `check_preflight_shortcut()`'s skip was over-broad. Component 3 (`stratified`/`thin-standard` for 400–5,000 lines) still materializes the full diff downstream. Therefore, `check_preflight_shortcut()` is perfectly safe to run for Component 3 commits (and desirable, as it correctly bypasses trivial-comment-only commits in that size range without needing LLM review). The structural incompatibility only applies to the new *oversized* (>5,000 lines) path, which never materializes the full diff. **Fix**: Retract the skip for Component 3; apply the skip *only* to the oversized path.

As written, Scenario 22/33's requirement was unimplementable; the data it refers to didn't exist anywhere upstream. **Fix**: `findings_freeze_data` must gain a `reviewed_files: list[str]` field, populated from whichever file selection (`high_risk_files` or `top_3_files`) actually determined the reviewed subset for that verdict; `rebuttal.py` reads this field to know which files to pass into `get_scoped_diff()`. **Claim 2 (disclosed, not blocking)**: migrating `_get_normalized_diff_hash()` from diff-text hashing to a full-commit-state hash (`git write-tree`) creates a transition window — any `.agent/state/rebuttal_pass.json` token or frozen gate-findings artifact created before this change deploys becomes silently incomparable against hashes computed after it deploys. This is a real, narrow operational note (internal harness state, not durable user-facing data) rather than a design flaw requiring dual-hash fallback complexity; logged as a residual risk rather than adding transitional-compatibility logic that would itself need eventual removal. **Claim 3 (disclosed, not blocking)**: once `rebuttal.py` uses `get_scoped_diff()` for oversized commits, the rebuttal auditor is blind to any file outside the originally-reviewed subset — a rebuttal genuinely needing cross-file context has no path to it except manually pasting content into the existing `evidence` field. No legitimate scenario requires the wizard to fire on a zero-file commit. No change made.
- v1.14 (2026-07-30, Claude): Twelfth adversarial review pass. **Claim 1 (critical, self-contradiction)**: v1.12's size pre-check specified "abort the moment `MAX_DIFF_CHARS` is exceeded," but §8's audit payload schema requires exact `original_lines`/`original_chars` integers — these cannot both hold under the same mechanism, since aborting early means the true total beyond the threshold is unknowable. **Fix**: the pre-check is a streaming counter, not an early-abort read — it reads the diff incrementally, incrementing line/char counters per chunk and discarding each chunk immediately (never buffering content, so memory stays O(1) regardless of diff size), but continues counting to the stream's natural end rather than halting at the threshold. The routing decision (oversized or not) can be made the moment the running counter first crosses the threshold; the counting itself continues so the audit payload gets an exact final total. This is a mechanism correction, not a relaxation of either requirement. **Claim 2 (real gap, distinct from Claim 3)**: the spec's "empty target_files → block via empty-slice guard" rule conflated two different causes with different correct outcomes: (a) every changed file was excluded by `skip_paths` (e.g. a huge generated `package-lock.json`) — nothing was ever eligible for review, and this should pass cleanly, consistent with how skip-listed changes are already treated regardless of size; (b) eligible (non-skip-listed) files existed, but high-risk/PageRank selection still yielded nothing (Scenario 34's actual case) — this should block, since something reviewable existed and wasn't captured. **Fix**: compute `eligible_files` (changed_files minus skip_paths matches) as an explicit intermediate step; if `eligible_files` is empty, pass cleanly (mirroring the existing `ALL_PATHS_SKIPPED` pattern); only escalate to the empty-slice guard's block if `eligible_files` is non-empty but selection into `target_files` still comes up empty. **Claim 3 (specific mechanism doesn't hold, underlying ambiguity is real)**: the claimed failure path (a `chmod +x`-only commit reaching `get_scoped_diff()` and triggering the empty-slice guard) doesn't follow from the spec as written — such a commit is tiny, stays within the hard ceiling, and never reaches Component 3's diff-fetching path per "Size-first control flow." However, the instruction "check `if not changed_files: return 0` **instead**" was genuinely ambiguous about whether this *replaces* the pre-existing `if not diff.strip(): return 0` check everywhere, or *adds* a new front-gate check specifically for the pre-diff-load routing decision. ## 3. Assumptions

- **[Resolved: PunchCard's governed arm runs under `enforcement.posture: strict`]** per the earlier posture-awareness decision (`SPEC-enforcement-postures.md` §9 trigger). HIB-078 and ratchet-specific concerns are therefore genuinely out of scope for this experiment, not just deprioritized.

- **[Resolved: HIB-068's fix mechanism is a hybrid, corrected from the original two-candidate framing]**. Direct inspection of `ai_review.py`'s `_run_review()` confirms:
  - A "Large Diff Stratified Review" mechanism (Component 3) already exists and already triggers regardless of pattern classification — any diff exceeding the configurable `large_diff_threshold` (default 400 lines) routes to either `stratified` (review the high-risk-file subset) or `thin-standard` (top-3 PageRank files) review. This is not new work to build.
  - The actual defect is ordering: the hard-ceiling checks (`MAX_DIFF_LINES=5000`, `MAX_DIFF_CHARS=200,000`) execute earlier in the function and `return 0` immediately on an oversized diff — before Component 3 ever runs. Component 3 is therefore currently unreachable for any diff that trips the hard ceiling.
  - **Chosen fix**: let the hard-ceiling path fall through into Component 3 instead of returning early. Since Component 3 was validated for the 400–5,000-line range and a diff tripping the *hard* ceiling could be substantially larger, introduce a second, smaller sanity ceiling evaluated on **both** dimensions — a config-driven `max_stratified_review_lines` (proposed default 2,000 lines) **and** `max_stratified_review_chars` (proposed default 80,000 characters), mirroring the two-dimensional check the existing hard ceiling already applies (`MAX_DIFF_LINES`/`MAX_DIFF_CHARS`). A line-count-only ceiling would pass a diff with few lines but a large single-file payload (e.g. a minified asset or JSON blob) straight through to the LLM. **Both ceilings apply to whichever file subset is actually routed to the LLM** — the high-risk-file subset under the `stratified` strategy, *or* the top-3 PageRank subset under the `thin-standard` fallback. The `thin-standard` path currently has no size check at all; both branches must be covered, not just `stratified`.
  - **Unified git-native pathspec diff retrieval (critical redesign, v1.10 — replaces `filter_diff_by_files()` entirely)**: Component 3 as it exists today only narrows *supporting context* — the actual diff payload sent to the LLM is still the full, unsliced original diff, requiring it to already be materialized in Python memory via `get_staged_diff()`. That materialization is exactly the unsafe operation this spec exists to eliminate for oversized diffs; slicing a pre-loaded string in Python doesn't avoid the OOM risk, it just moves where the crash happens. **Fix**: add a `get_scoped_diff(target_files: list[str]) -> str` helper. `get_scoped_diff()` must check `if not target_files: return ""` in Python **before** invoking git at all — passing an empty pathspec list to `git diff --cached --unified=3 --` diffs the *entire* repository (git's standard behavior for an unrestricted pathspec), which would silently defeat the memory-safety design if `target_files` is ever empty (a reachable case: `get_pagerank_scores()` can return `{}` on failure, making `top_3_files` empty too). This helper fetches diff content directly from git via pathspec (`git diff --cached --unified=3 -- <file1> <file2> ...`) — git computes and returns only the diff for the specified files, and the full diff is never materialized. `filter_diff_by_files()` was never actual codebase code — it was this same spec's own earlier proposed function (v1.3–v1.9), superseded here by `get_scoped_diff()`'s git-native design. This helper is used uniformly for **both** the existing Component 3 range (400–5,000 lines, whether `stratified` selects high-risk files or `thin-standard` falls back to top-3 PageRank files) **and** the new oversized (>5,000 lines) path — one mechanism, not two. `rebuttal.py` uses the same helper against the file list recorded in the frozen gate-findings artifact, rather than calling `get_staged_diff()` at all.
  - **Command-line argument limit safety (critical, v1.15)**: `target_files` must never be passed to git as literal command-line arguments — every OS has a hard command-line length limit (`ARG_MAX` on Linux/macOS, ~32,767 characters on Windows), and `high_risk_files` (unlike the capped-at-3 `top_3_files`) has no size bound in this design. A sufficiently large file selection would raise `OSError`, which `main()`'s existing fail-open handler would silently swallow, defeating the entire memory-safety redesign via a different mechanism than the one it was built to close. `get_scoped_diff()` must pass `target_files` via `git diff --cached --unified=3 --pathspec-from-file=-`, writing paths to the subprocess's stdin rather than as command-line arguments, regardless of how many files are selected.
  - **Two prior fixes are retired as obsolete by this redesign, not silently dropped**: exact path-boundary matching against the `diff --git a/<path> b/<path>` header (v1.8) and quote-tolerant header matching (v1.9) no longer apply — there is no diff header to parse or match once git's own pathspec resolves target files natively (exact-match by default for literal paths, no substring risk). The `-z`/quote-safety requirement for the `changed_files` *listing* itself remains necessary, since that list still determines which files get selected before the scoped fetch runs.
  - **Bounded read for single-file safety (defense-in-depth)**: even scoped pathspec fetching could still risk memory pressure if one individually-selected file is itself enormous (e.g. a multi-gigabyte blob flagged high-risk). `get_scoped_diff()` must use a bounded/streaming read (`subprocess.Popen`, reading incrementally and aborting once output exceeds `max_stratified_review_chars`) rather than `capture_output=True`, so a single oversized file's content triggers the sanity-ceiling block path rather than a memory crash.
  - **Empty-slice guard**: if `get_scoped_diff()` produces an empty or whitespace-only sliced sub-diff (the reviewed subset resolves to no matching hunks), the gate must not send `""` to `provider.review()` — an empty diff would produce a false "0 findings, all clean" verdict on a commit that was never genuinely reviewed. Treat this case as failing the sanity ceiling (`oversized_diff_blocked`), requiring the same override path as an over-large sub-diff.
  - **Size-first control flow (critical redesign, v1.11/v1.12)**: v1.10 replaced the downstream slicing mechanism but never gated the upstream `diff = get_staged_diff()` call, which remained unconditional — meaning the original `MemoryError` → fail-open vulnerability was still fully reachable via the primary review path regardless of the redesign. **Fix**: a size pre-check must run first, before the `SKIP_AI_REVIEW` block, and must decide the *entire* subsequent code path, not just whether the bypass blocks are skipped. **Size pre-check without buffering**: determine if the diff is oversized *before* parsing headers or loading its contents. The pre-check must use a streaming counter, not an early-abort read: read the diff incrementally in chunks via `subprocess.Popen`, incrementing running line/char counters per chunk and discarding each chunk's content immediately after counting (never buffering the diff text, so memory use stays O(1) regardless of diff size) — but continue counting to the stream's natural end rather than halting the moment a threshold is crossed. The *routing decision* (oversized or not) can be made as soon as the running counter first exceeds `MAX_DIFF_LINES`/`MAX_DIFF_CHARS`; the counting itself continues so an exact final `original_lines`/`original_chars` total is available for the audit payload (§8) — aborting early would make the payload's exactness requirement mathematically unsatisfiable, which is exactly the contradiction this correction closes. **Encoding safety (v1.16)**: the streaming read must explicitly specify `errors="replace"` (matching `get_staged_diff()`'s own established pattern for exactly this reason) — without it, a binary file slipping past `.gitignore` within an oversized diff could raise `UnicodeDecodeError` mid-stream, crashing into `main()`'s fail-open handler via a new vector, the exact failure class this spec exists to close.
    - **Within the hard ceiling** (`≤ MAX_DIFF_LINES`/`≤ MAX_DIFF_CHARS`): existing flow is safe and unchanged — `get_staged_diff()` is called, the full diff is materialized (bounded and safe at this size by definition), and passed to `load_review_context()`, `get_recent_file_churn()`, Component 3, etc. as today.
    - **Exceeding the hard ceiling**: `get_staged_diff()` must **never be called**, at any point in the remaining execution. Determine `changed_files` via `git diff --cached --name-only -z` (already cheap, already required). Perform high-risk/top-3 file selection using only file paths — no diff content needed for this step. Any downstream function that currently takes the full diff as a parameter (`load_review_context(diff)`, `get_recent_file_churn(diff)`, and any other consumer of the raw `diff` variable before Component 3's file selection point) must be adapted to receive `get_scoped_diff()`'s result instead, or be explicitly skipped for this path if it cannot be meaningfully adapted (`check_preflight_shortcut()` — see the retraction above — is the confirmed case requiring skip rather than adaptation; audit for any other such consumer before implementation).
    - This pre-check must divert oversized diffs around **both** the `SKIP_AI_REVIEW` env-var block **and** the deprecated `.skip-ai-review` sentinel-file bypass (unchanged from v1.10) — a diff routed around one but not the other would still leak through the unprotected path.
  - **Full-commit integrity hash, independent of scoped diff text (critical, v1.12)**: `_get_normalized_diff_hash()` is currently a full-commit integrity lock — it's what confirms, at rebuttal time, that nothing has changed since the original FAIL. Once `get_scoped_diff()` becomes the primary diff representation for oversized commits, this hash must **not** be computed against the scoped subset — doing so would let a developer fail review on a high-risk file, quietly modify an *excluded, unreviewed* file, and successfully rebut the original finding while the tampered file rides along undetected. The hash must cover full commit state (e.g. via `git write-tree`, or an equivalent index-state hash) regardless of which files were actually sent to the LLM. This applies to both `ai_review.py`'s frozen gate-findings artifact (`diff_hash` field) and `rebuttal.py`'s contemporaneity check — both must use the same full-commit-state hash, not diff text of any kind.
  - **Frozen gate-findings artifact must record the reviewed file list (critical, v1.13)**: `render_review()`'s `findings_freeze_data` dict currently contains only `session_id`, `timestamp`, `diff_hash`, `verdict`, and `findings` — it does not record which files were actually selected into the reviewed subset (`high_risk_files` under `stratified`, or `top_3_files` under `thin-standard`). Without this, `rebuttal.py` has no way to know which files to pass into `get_scoped_diff()` to reconstruct the exact sub-diff a rebuttal needs to reference — the data this spec's own Scenario 22/33 assume exists was never actually specified as being written. **Fix**: add `reviewed_files: list[str]` to `findings_freeze_data`, populated from whichever file selection determined the reviewed subset for that verdict. `rebuttal.py` reads this field (not `changed_files` or any other reconstruction) to call `get_scoped_diff(reviewed_files)` identically to how the original review computed its sub-diff. **Standard-review coverage (v1.15)**: Component 3's file selection (`high_risk_files`/`top_3_files`) never runs for standard reviews (diffs under `large_diff_threshold`) — these review the full `eligible_files`-filtered diff directly. For this case, `reviewed_files` must be populated with `eligible_files` (the same `changed_files`-minus-`skip_paths` set introduced in v1.14), not left undefined or empty. Without this, `rebuttal.py` would crash or silently evaluate an empty diff for the majority of real-world FAIL verdicts, since standard reviews (not Component 3 or oversized) are the common case.
  - **Genuine-empty-commit check decoupled from diff content (v1.12)**: the pre-existing `if not diff.strip(): return 0` check (for genuinely empty commits, e.g. empty merges) and the v1.7 empty-slice guard (an empty *scoped* result must block, not fast-pass) would silently collide once `get_staged_diff()` is removed for the oversized path — retargeting the empty check to `get_scoped_diff()`'s result would incorrectly fast-pass an oversized commit with zero files selected for review, rather than blocking it as the empty-slice guard requires. **Fix**: check `if not changed_files: return 0` instead, decoupled from diff content entirely — this signal is available regardless of which path is taken and correctly represents "nothing was staged," distinct from "nothing was selected into the reviewed subset." This check must not fire unconditionally on empty `changed_files` — see the "Amend-awareness for the front-gate check" bullet immediately following, which is a required refinement to this check, not a separate mechanism.

  - **Distinguishing two causes of an empty target-file selection (v1.14)**: an empty `target_files` list can arise from two different situations requiring different outcomes, previously conflated. Compute `eligible_files` (i.e. `changed_files` after `skip_paths` filtering) as an explicit intermediate step: if `eligible_files` is empty (every changed file was skip-listed — e.g. a huge generated `package-lock.json`) — nothing was ever eligible for review, and this should pass cleanly, consistent with how skip-listed changes are already treated regardless of size. Only escalate to the empty-slice guard's block (Scenario 14/34) if `eligible_files` is non-empty but high-risk/PageRank selection into `target_files` still yields nothing — that is a genuine selection failure, not a deliberate exclusion, and should block.

  - **Scope clarification (v1.14)**: this `changed_files`-based check is a new front-gate check enabling the routing decision before any diff is loaded — it does not replace the pre-existing `if not diff.strip(): return 0` check, which remains unchanged within the standard/Component-3 path (where a real `diff` variable exists after `get_staged_diff()` runs) and continues to correctly fast-pass mode-only-change or empty-deletion commits there, exactly as it does today. The two checks serve different code paths and both remain necessary.
  - **Amend-awareness for the front-gate check (critical, v1.16)**: `get_staged_diff()` already has a working amend-recovery mechanism (documented in its own docstring as `BUG-03`) — it detects `git commit --amend` via `git rev-parse --verify ORIG_HEAD` and falls back to comparing `HEAD~1..HEAD` when `--staged` is empty. Today, `_run_review()` never short-circuits before this recovery gets a chance to run: an empty `changed_files` list does not currently cause an early return. The `if not changed_files: return 0` front-gate check specified above would insert a hard return *before* `get_staged_diff()` is ever called, permanently defeating this recovery for every `--amend` commit with no newly-staged content. **Fix**: the front-gate check must itself test `git rev-parse --verify ORIG_HEAD` before concluding "genuinely nothing staged, safe to fast-pass." If `ORIG_HEAD` exists (amend in progress) and `changed_files` is empty, do **not** fast-pass — fall through to the normal flow so `get_staged_diff()`'s existing recovery logic can run. Only fast-pass via this front-gate when `ORIG_HEAD` does not exist, confirming this is a genuinely empty commit, not an amend.

  - **Deprecated `.skip-ai-review` sentinel bypass (critical, found in review round 8)**: a completely separate, previously-unaddressed bypass exists in the code — `if (PROJECT_ROOT / ".skip-ai-review").exists(): ... return 0` — unconditional, zero content validation, distinct from the structured `.skip-ai-reason.json` mechanism this spec extends. This bypass is already self-marked deprecated by its own print statement (`"'.skip-ai-review' bypass file is deprecated. Use 'enforcement.posture: observe'..."`). Given it provides no structure to extend and actively undermines this spec's hardening goal, remove this block outright rather than merely routing oversized diffs around it — leaving a working-but-deprecated silent bypass in place would be inconsistent with the rest of this spec's intent.
  - **`changed_files` path-quoting hardening**: the file-list retrieved via `git diff --cached --name-only` must account for git's path-quoting behavior (`core.quotePath`, default on) for paths containing non-ASCII characters, backslashes, double-quotes, or control characters — such paths are C-escaped and wrapped in double quotes in git's default output, which would break plain `.strip()`-based file-list parsing. Use `git diff --cached --name-only -z` (null-terminated, always unquoted) for the file list.
  - **Multi-pass consensus safety on sliced diffs**: `shuffle_diff_hunks()` provides no entropy when the sliced diff contains ≤1 file, so a hallucinated finding would repeat identically across every pass of `AI_REVIEW_PASSES > 1`, defeating the `consensus_filter`'s `>50%` threshold as a safeguard rather than reinforcing it. When a diff has been sliced, clamp `AI_REVIEW_PASSES` to 1 for that review.
  - **Preflight shortcut retraction for oversized paths (corrected, v1.12)**: `check_preflight_shortcut()`'s `PASS_FAST` verdict is commit-level — it exits the entire gate. Running it against a scoped sub-diff creates a vulnerability (a massive commit whose high-risk subset is trivial would issue a full-commit pass). However, v1.11's fix to skip it for *both* Component 3 and the oversized path was over-broad: Component 3 (within the hard ceiling) still materializes the full diff, so the function can run safely and correctly against the full diff there. `check_preflight_shortcut()` must be **skipped entirely only for the oversized (>5,000 lines) path** which never materializes the full diff. It remains active for the standard and Component 3 paths.
  - **Escape valve mechanism**: not a commit-message trailer. `ai_review.py` runs at the `pre-commit` hook stage, and `get_commit_message()` cannot read `COMMIT_EDITMSG` at that stage (confirmed in code — it only falls back to reading the message file when `PRE_COMMIT_HOOK_STAGE != "pre-commit"`), so a trailer-based override would be an inescapable deadlock. Instead, extend `ai_review.py`'s own existing `SKIP_AI_REVIEW`/`SKIP_REASON`/`.skip-ai-reason.json` mechanism — already a structured, auditable override path for high-risk commits, with an interactive TTY wizard and staleness detection already built. This is a genuine existing precedent, verified directly in the code. **Concrete integration requirements**, confirmed necessary by direct inspection of the existing validation logic:
    - Add `OVERSIZED_DIFF` to `VALID_REBUTTAL_TYPES` (currently a closed 5-value set: `FALSE_POSITIVE`, `SPEC_REQUIREMENT`, `ARCHITECTURAL_INVARIANT`, `OUT_OF_SCOPE`, `REMEDIATED`) and accept a sentinel `finding_ids` value (e.g. `["HIB-068"]`) for it, since the existing validation requires a non-empty `finding_ids` list and an oversized-diff block has no findings to reference.
    - `ai_review.py` carries its own hardcoded fallback tuple of `VALID_REBUTTAL_TYPES` (used only if importing `rebuttal.py` fails) — this must be updated to include `OVERSIZED_DIFF` alongside the primary update in `rebuttal.py`, or a degraded-import path would silently reject the new override type.
    - Add a 6th option to the interactive TTY wizard (Vector C) for `OVERSIZED_DIFF`.
    - For this rebuttal type specifically (not universally, to avoid changing established behavior for the five pre-existing types, tracked separately as **HIB-085**): reject a stale `.skip-ai-reason.json` with `sys.exit(1)` rather than the existing behavior of warning and proceeding anyway — PunchCard's experimental integrity requires a session-contemporaneous override, not one that could be hours or days old.
    - In non-TTY/CI environments (where the wizard cannot run), print explicit copy-paste override guidance, matching the existing pattern already used by `_handle_parse_failure`/`_handle_api_unavailable` (e.g. `SKIP_AI_REVIEW=1 SKIP_REASON='{"rebuttal_type":"OVERSIZED_DIFF","finding_ids":["HIB-068"],"evidence":"<reason>"}'`).
    - **TTY wizard reachability**: the wizard must not be nested inside the existing `if is_hr:` branch — it must be reachable for any blocked oversized commit regardless of `is_hr`, per the bypass-routing fix above, so a `thin-standard` (non-high-risk) oversized commit can access the `OVERSIZED_DIFF` wizard option on retry.
    - **Atomic bypass-file consumption**: the existing `.skip-ai-reason.json` consume pattern (`read_text()` then `unlink()`) has a TOCTOU window between read and delete. Use an atomic claim (e.g. `os.replace()` to a temp path before reading, or an equivalent atomic rename) so two concurrent processes cannot both read the same single-use token before either consumes it.
  - **Exit code**: when the sanity ceiling is exceeded and no override is present, the gate must call `sys.exit(1)`. The current hard-ceiling checks both `return 0`; this must change, not merely gain a log line.
  - **Legacy hard-ceiling block removal (explicit, not implied)**: the existing `if diff_lines > max_lines:` and `if diff_chars > max_chars:` blocks — and their `return 0` statements — must be deleted outright, not left in place with new logic appended after an unreachable early return. "Fall through into Component 3" means these blocks no longer exist as early-exit gates; the new sanity-ceiling check (on the reviewed subset, per the bullets above) is what supersedes them.
  - **Audit log completeness on block**: before calling `sys.exit(1)` when the sanity ceiling is exceeded with no override present, `ai_review.py` must call `_persist_verdict(fail_open_reason="OVERSIZED_DIFF_BLOCKED: ...")` with a FAIL-equivalent verdict, matching the existing pattern used by `_handle_parse_failure` and the pre-existing `DIFF_TOO_LARGE_FAILOPEN` path. Without this, `.ai-review-log.jsonl` has no record of the blocked commit even though `harness_events.jsonl` does.
  - **`skip_paths`/`changed_files` sync**: `changed_files` (used for `get_high_risk_files()` and PageRank top-3 selection) must be filtered against `skip_paths` (e.g. `package-lock.json`) identically to how diff-text is currently filtered. High-risk matching must not evaluate ignored paths. This filtering step produces `eligible_files`, the basis for the empty-target-selection distinction above (v1.14) — not merely a pre-filter on the diff text, but the explicit signal that determines whether an empty selection means "nothing was eligible" (pass) or "something was eligible but not selected" (block).
  - **Config fallback safety**: `max_stratified_review_lines`/`max_stratified_review_chars` must not be read via a bare `config.get(...)` that could return `None` into a numeric comparison (`TypeError` on a pre-v1.4.14 or not-yet-migrated `.agent/config.yaml`). Extend `_load_review_config()`'s existing pattern — pre-set Python-level defaults (2,000 / 80,000) before attempting to read the config file, overwrite only on successful parse — matching how `large_diff_threshold`/`large_diff_strategy` are already handled safely in the same function. Do not introduce a separate fallback mechanism.
  - **Agent self-override risk**: because the override path is env-var/file-based, an autonomous agent operating in PunchCard's governed arm could in principle self-invoke it without human involvement. The override's audit event must be distinguishable enough that post-hoc analysis of `harness_events.jsonl` can detect whether an agent autonomously used the escape hatch during an experimental run (see Scenario 3).
  - This removes the prior citation of "T1-G-15's `COMPLEXITY-ACCEPTED` pattern" as precedent — T1-G-15 is an undelivered v1.5.0 backlog item (confirmed `⬜` in `FRAMEWORK_ROADMAP.md`); no such pattern exists in the codebase today.

## 4. Acceptance Criteria

### Scenario 1: Oversized diffs are routed into review, not silently failed open (HIB-068)

**Given** a commit whose diff exceeds `max_diff_lines` (the hard ceiling) but whose reviewed subset — the high-risk-file subset under `stratified` strategy, or the top-3 PageRank subset under `thin-standard` fallback — is within the new sanity ceiling
**When** the AI review gate evaluates it
**Then** the gate does not return a bare `FAIL_OPEN` / `DIFF_TOO_LARGE_FAILOPEN` pass-through
**And** instead falls through into the existing stratified/thin-standard review mechanism (Component 3), with `get_scoped_diff()` fetching only the reviewed subset's content directly from git via pathspec — the full original diff is never materialized in Python memory at any point in this path.

### Scenario 2: The escape valve is used only when the reviewed subset itself would be infeasible, and blocks with the correct exit code

**Given** a commit whose diff exceeds `max_diff_lines` **and** whose reviewed subset (high-risk-file or top-3 PageRank, whichever strategy applies) also exceeds the new, smaller sanity ceiling (`max_stratified_review_lines`)
**When** the gate evaluates it with no override present
**Then** the gate calls `sys.exit(1)`, blocking the commit — not a bare `return 0`
**And** in a TTY environment, the interactive wizard offers an `OVERSIZED_DIFF` option accepting a sentinel `finding_ids` value (e.g. `["HIB-068"]`) rather than requiring a real finding reference
**And** in a non-TTY/CI environment, the gate prints an explicit copy-paste `SKIP_AI_REVIEW`/`SKIP_REASON` command
**And** a stale `.skip-ai-reason.json` (predating the current session) is rejected with `sys.exit(1)` for this override type specifically, not silently accepted with only a warning
**And** once a valid, fresh override is supplied, the commit proceeds with a `high_risk_gate_override`-pattern audit event recorded, distinct from the pre-existing `large_diff_fail_open` event type.

### Scenario 3: An agent-invoked override is distinguishable from a human-invoked one

**Given** the escape valve from Scenario 2 was used
**When** `harness_events.jsonl` is inspected after the fact
**Then** the audit event contains enough information (e.g. whether the override was supplied via the interactive TTY wizard vs. a pre-set environment variable, and by which actor per session ledger attribution) to distinguish a human-confirmed override from one an autonomous agent could have self-invoked without human involvement — this is a PunchCard-specific requirement, since an undetectable agent self-override would silently invalidate the governed arm's experimental condition.

### Scenario 4: Existing T1-K-14 audit taxonomy is preserved

**Given** the existing `large_diff_fail_open` event type and `FAIL_OPEN` verdict schema from T1-K-14
**When** HIB-068's fix lands
**Then** no existing consumer of that event type or verdict schema breaks — this is a behavior change on top of the taxonomy, not a replacement of it.

### Scenario 5: RISK-001 is genuinely verified, not just re-read (Peter, human-operator-only)

**Given** `KNOWN_RISKS.md`'s RISK-001 entry and its four-step verification procedure
**When** this spec's Phase 1 completes
**Then** RISK-001's status field reflects an actual outcome (`Verified` / `Verified with caveats` / `Failed — see remediation`) with the specific evidence recorded (e.g. hook fired, session traceability confirmed, outcome override worked correctly), not left as `Unverified` or updated without a real session having been run.

### Scenario 6: State persistence self-containment is verified (Peter, human-operator-only)

**Given** a live Antigravity session
**When** `.agent/state/session.json` is inspected during and after that session
**Then** its writes and reads are confirmed independent of any Antigravity-internal state store, with the specific check performed documented in `KNOWN_RISKS.md` or an equivalent record.

### Scenario 7: Harness version for the experiment is a recorded decision

**Given** `harness_version.txt`'s current value
**When** this spec's Phase 3 completes
**Then** a decision is recorded (via `record_decision()` / `log_decision.py`) stating which harness version PunchCard will run against and why, rather than the version being whatever happens to be checked out when the experiment starts.

### Scenario 8: The agent-self-override check is a committed action, not just a capability

**Given** Scenario 3's audit-distinguishability requirement is implemented
**When** this spec's Phase 4 completes
**Then** a decision is recorded (via `record_decision()` / `log_decision.py`) explicitly committing to inspect `harness_events.jsonl` for `oversized_diff_override_accepted` events — with specific attention to agent-vs-human actor attribution — as part of PunchCard's post-run analysis, so the detectability this spec builds has an actual owner rather than existing as an unused capability.

### Scenario 9: `ai_review.py`'s `_find_project_root()` includes the walk-up-from-`__file__` fallback (HIB-084, partial)

**Given** `ai_review.py`'s `_find_project_root()` function
**When** invoked from a working directory that is neither the project root nor resolvable via `git rev-parse --show-toplevel` (e.g. git unavailable, or running outside a git worktree)
**Then** the function walks up from `__file__`'s location checking for `.agent` or `.git` markers before falling back to the fixed-depth `SCRIPT_DIR.parent.parent` guess — matching the canonical pattern specified in HIB-084 (cwd fast-path → git rev-parse → walk-up-from-file → fixed-depth last resort), rather than skipping directly from git-based resolution to the fragile fixed-depth guess.

### Scenario 10: The sanity ceiling checks both line count and character count

**Given** a commit whose reviewed subset (high-risk-file or top-3 PageRank) is under `max_stratified_review_lines` but exceeds `max_stratified_review_chars` (e.g. a small number of lines containing a large minified or single-line-blob file)
**When** the gate evaluates the sanity ceiling
**Then** it is treated as exceeding the sanity ceiling — the same escape-valve/block behavior as Scenario 2 — rather than passing through to `provider.review()` on a character-count basis the line-only check would have missed.

### Scenario 11: The rebuttal-type fallback tuple stays in sync

**Given** `ai_review.py`'s hardcoded fallback `VALID_REBUTTAL_TYPES` tuple (used only when importing `rebuttal.py` fails)
**When** `OVERSIZED_DIFF` is added to `rebuttal.py`'s canonical `VALID_REBUTTAL_TYPES`
**Then** the fallback tuple in `ai_review.py` is updated identically, so a degraded-import path does not silently reject the `OVERSIZED_DIFF` override.

### Scenario 12: Blocked oversized-diff commits are recorded in both audit logs

**Given** an oversized diff blocked by `sys.exit(1)` with no override present
**When** the block occurs
**Then** `_persist_verdict()` is called with a FAIL-equivalent verdict before the exit, so `.ai-review-log.jsonl` records the blocked attempt in addition to the `oversized_diff_blocked` event already written to `harness_events.jsonl`.

### Scenario 13: `skip_paths`-matched files are excluded from Component 3's file selection

**Given** a changed file that matches both a `skip_paths` pattern and a high-risk-file pattern
**When** Component 3 selects the high-risk-file subset (or the top-3 PageRank subset under `thin-standard`)
**Then** that file is excluded from the reviewed subset, consistent with its exclusion from the diff text itself — `changed_files` and the diff text agree on which files are actually in scope for review.

### Scenario 14: An empty sliced sub-diff is treated as a block, not a false pass

**Given** `get_scoped_diff()` produces an empty or whitespace-only sliced sub-diff for the reviewed subset
**When** the gate evaluates the result
**Then** it is treated as failing the sanity ceiling (`oversized_diff_blocked`, override required) rather than being sent to `provider.review()` as an empty diff, which would otherwise produce a false "all clean" verdict on an unreviewed commit.

### Scenario 15: Missing config keys fall back safely, not to a crash

**Given** `.agent/config.yaml` does not yet define `max_stratified_review_lines` or `max_stratified_review_chars` (e.g. a pre-v1.4.14 installation)
**When** `_load_review_config()` runs
**Then** it returns the Python-level defaults (2,000 lines / 80,000 characters) rather than `None`, consistent with how `large_diff_threshold`/`large_diff_strategy` are already defaulted in the same function — no `TypeError` on the subsequent comparison.

### Scenario 16: Oversized-diff override routing applies regardless of `is_hr`

**Given** a commit whose diff is oversized (exceeds the existing hard ceiling), whether or not it is classified `is_hr`
**When** `SKIP_AI_REVIEW=1` is set with no structured `OVERSIZED_DIFF` reason
**Then** the commit is not bypassed via the pre-existing top-level `SKIP_AI_REVIEW` block (neither the `is_hr` structured-validation branch nor the `else` unconditional-pass branch) — it proceeds into the normal diff-loading/Component-3/sanity-ceiling pipeline, where `OVERSIZED_DIFF`-specific validation is evaluated.

### Scenario 17: The TTY wizard is reachable for non-high-risk oversized commits

**Given** a `thin-standard` (non-high-risk) commit blocked for exceeding the sanity ceiling
**When** the commit is retried in a TTY environment
**Then** the interactive wizard's `OVERSIZED_DIFF` option is reachable and offered, not skipped due to the commit's `is_hr` classification.

### Scenario 18: Audit payload records an observable vector, not an inferred actor

**Given** an `oversized_diff_override_accepted` event
**When** the payload is written
**Then** it includes `"vector": "tty | env | file"` (which override mechanism fired, mechanically observable) rather than a guessed `"actor": "agent | human"` field; actor attribution for PunchCard's post-run analysis is derived separately by joining this event against `session_ledger.jsonl`, not captured at event-write time.

### Scenario 19: Bypass-file consumption is atomic

**Given** two processes attempting to read `.skip-ai-reason.json` at nearly the same time
**When** the consume-on-read logic executes
**Then** only one process successfully claims and consumes the file (via an atomic operation, e.g. `os.replace()` to a temp path before reading) — no window exists in which both processes could read the token before either deletes it.

### Scenario 20: [Retired, v1.10] Exact path-boundary matching

This scenario is retired — it validated `filter_diff_by_files()`'s header-matching logic, which no longer exists after the v1.10 redesign. Git's own pathspec resolution for literal target paths is exact by default; there is no diff-header string to parse or match. See the v1.10 changelog entry for the full rationale.

### Scenario 21: Multi-pass review is clamped to single-pass on sliced diffs

**Given** a diff that has been sliced (containing few enough files that `shuffle_diff_hunks()` provides no meaningful entropy)
**When** the review runs
**Then** `AI_REVIEW_PASSES` is clamped to 1 for this review, rather than running multiple passes whose `consensus_filter` safeguard would be defeated by identical repeated output across passes.

### Scenario 22: Rebuttal evaluates against the same context subset as the original review

**Given** a commit that was blocked after undergoing Component 3's stratified or thin-standard review (or an oversized diff using the same file-selection logic)
**When** a developer attempts to rebut the findings
**Then** `rebuttal.py` uses `get_scoped_diff()` to retrieve only the diff context for the files that were originally reviewed, rather than fetching the full diff via `get_staged_diff()`. This ensures the rebuttal auditor LLM evaluates the developer's arguments against the exact same partial codebase view the original reviewer used. This requires `render_review()`'s frozen gate-findings artifact to include a `reviewed_files` field recording the exact file selection used for the original review — without it, `rebuttal.py` has no source for the file list `get_scoped_diff()` requires.

### Scenario 23: The size pre-check never materializes the full diff in memory

**Given** a commit whose staged diff is large enough that fully buffering it in memory would be unsafe (e.g. an accidentally-staged multi-gigabyte file)
**When** the gate's size pre-check runs (before the `SKIP_AI_REVIEW` block, per the bypass-routing fix)
**Then** it determines oversize status via a streaming counter that reads incrementally and discards each chunk immediately (never buffering content, so memory stays O(1) regardless of diff size), continuing to count to completion so an exact final size is available for the audit payload, rather than an early-abort read that would make exact reporting impossible — never via `get_staged_diff()` or any call that fully materializes the diff text — so a `MemoryError` cannot occur at this stage and cannot be caught by `main()`'s fail-open handler.

### Scenario 24: The legacy hard-ceiling blocks no longer exist as early-exit gates

**Given** `ai_review.py`'s source after Phase 0 lands
**When** the code is inspected
**Then** the original `if diff_lines > max_lines: ... return 0` and `if diff_chars > max_chars: ... return 0` blocks are absent — not present-but-unreachable — confirming the new sanity-ceiling logic is what actually governs oversized-diff handling, not dead legacy code sitting alongside it.

### Scenario 25: `changed_files` listing is quote-safe (diff-header quote-tolerance retired, v1.10)

**Given** a staged file whose path contains a character git's `core.quotePath` would escape and quote (non-ASCII, backslash, double-quote, or control character)
**When** the gate builds its changed-files list for high-risk/top-3 selection
**Then** the file list is obtained via `git diff --cached --name-only -z` (always unquoted), so such a file is not invisible to high-risk/ADR classification or file selection.

The previously-paired "diff-git header tolerates git's quoted header form" requirement (v1.9) is retired — after the v1.10 redesign, no diff header is ever parsed; `get_scoped_diff()` passes file paths directly to git's pathspec argument, which resolves literal paths exactly regardless of quoting in git's display output.

### Scenario 26: Oversized-diff padding incentive is logged as a known, unmitigated risk

**Given** this spec's Known Residual Risks section
**When** reviewed
**Then** it explicitly names the theoretical incentive to pad a commit past the hard ceiling (5,000 lines/200,000 chars) to access the lower-friction `OVERSIZED_DIFF` override instead of genuine review, without claiming this spec mitigates it — an honest disclosure rather than a silent gap.

### Scenario 27: A single oversized selected file does not crash the scoped fetch

**Given** a high-risk or top-3-selected file whose individual diff content is itself large enough that a full in-memory read would risk `MemoryError`
**When** `get_scoped_diff()` fetches its content
**Then** it reads via a bounded/streaming method that aborts once output exceeds `max_stratified_review_chars`, treating this as hitting the sanity ceiling (the same block/override path as Scenario 2) rather than risking a memory crash.

### Scenario 28: The deprecated `.skip-ai-review` sentinel bypass no longer exists

**Given** `ai_review.py`'s source after Phase 0 lands
**When** the code is inspected
**Then** the `if (PROJECT_ROOT / ".skip-ai-review").exists(): ... return 0` block is absent — removed outright, not merely routed around — since it provided no structured validation and was already self-marked deprecated.

### Scenario 29: [Retracted, v1.11] `check_preflight_shortcut()` runs against the scoped diff

This scenario is retracted, not merely corrected — the requirement it specified (run `check_preflight_shortcut()` against `get_scoped_diff()`'s result) was itself a vulnerability: `PASS_FAST` is a commit-level bypass, and evaluating it against a coincidentally-trivial sub-diff would silently bypass an entire oversized commit's review. The correct fix, per v1.11, is to skip `check_preflight_shortcut()` entirely for Component 3/oversized paths. See Scenario 30.

### Scenario 30: `check_preflight_shortcut()` is skipped entirely for the oversized path

**Given** a commit routed through the oversized (>5,000 lines) path
**When** `_run_review()` executes
**Then** `check_preflight_shortcut()` is not called at all for this commit, because the full diff is never materialized and a scoped sub-diff cannot safely issue a full-commit `PASS_FAST` verdict.
**And given** a commit routed through Component 3 (400–5,000 lines)
**When** `_run_review()` executes
**Then** `check_preflight_shortcut()` *is* still called against the full materialized diff, correctly bypassing trivial commits in that size tier.

### Scenario 31: An empty target-file list never triggers a full-repository diff

**Given** `get_scoped_diff()` is called with an empty `target_files` list (e.g. `get_pagerank_scores()` failed, leaving `top_3_files` empty)
**When** the function executes
**Then** it returns `""` immediately via a Python-level check, without ever invoking `git diff` — an empty pathspec passed to git would otherwise diff the entire repository, defeating the memory-safety design.

### Scenario 32: `get_staged_diff()` is never called anywhere in the oversized execution path

**Given** a commit whose diff exceeds the hard ceiling (`MAX_DIFF_LINES`/`MAX_DIFF_CHARS`)
**When** `_run_review()` processes it, from the initial size pre-check through Component 3, the sanity ceiling check, and the LLM review
**Then** `get_staged_diff()` is not called at any point in this execution — file selection uses only `changed_files` (from `--name-only -z`), and all diff-content needs are satisfied exclusively via `get_scoped_diff()`. This is distinct from Scenario 23 (which covers only the initial size pre-check) — this scenario covers the *entire* downstream execution path.

### Scenario 33: Rebuttal integrity anchors to the full commit state, not the sliced diff

**Given** a commit that was blocked or flagged during a scoped review (oversized path)
**When** a developer attempts to rebut the findings
**Then** `rebuttal.py` retrieves the artifact and verifies its `diff_hash` against the full index state (e.g. `git write-tree`), not against a hash of the sliced sub-diff
**And** any tampering with unreviewed files in the working directory since the gate ran causes the rebuttal to fail the integrity check, closing the tamper-leak vulnerability.

### Scenario 34: An eligible-but-unselected commit blocks; a fully-excluded commit does not

**Given** an oversized commit where `eligible_files` (changed files after `skip_paths` filtering) is non-empty, but high-risk/top-3 file selection still resolves to zero files (e.g. no high-risk files matched, and PageRank scoring failed)
**When** the gate evaluates whether to fast-pass or block
**Then** it correctly blocks per the empty-slice guard (Scenario 14, `oversized_diff_blocked`) — because eligible, reviewable files existed and were not captured by selection.

**Given**, separately, an oversized commit where `eligible_files` is empty (every changed file was excluded by `skip_paths` — e.g. a huge generated `package-lock.json`)
**When** the gate evaluates it
**Then** it passes cleanly, consistent with the existing `ALL_PATHS_SKIPPED` pattern for skip-listed changes — nothing was ever eligible for review, so this is not a selection failure and must not trigger the empty-slice guard's block.

### Scenario 35: A genuinely empty commit exits cleanly before either guard applies

**Given** a genuinely empty commit (`git diff --cached --name-only -z` returns no files)
**When** the gate evaluates it
**Then** it exits cleanly (`return 0`) immediately via the `changed_files`-based check, without ever reaching the empty-slice guard.


### Scenario 38: An `--amend` commit with no newly-staged content still gets reviewed

**Given** a developer runs `git commit --amend` with no new files staged (e.g. editing only the commit message, or amending to reuse the same tree)
**When** the gate's front-gate `changed_files` check evaluates it
**Then** it detects the amend via `git rev-parse --verify ORIG_HEAD` and does **not** fast-pass — it falls through to `get_staged_diff()`, whose existing `HEAD~1..HEAD` recovery logic reconstructs the amended commit's actual diff for review, exactly as it does today prior to this spec's changes.

### Scenario 39: The streaming size pre-check does not crash on non-UTF-8 content

**Given** a staged diff containing a binary file or non-UTF-8 byte sequence that slipped past `.gitignore`
**When** the streaming size pre-check reads the diff incrementally
**Then** it uses `errors="replace"` (matching `get_staged_diff()`'s established pattern) and does not raise `UnicodeDecodeError` — no crash reaches `main()`'s fail-open handler via this path.

## 6. Alternatives Considered

- **A — Skip HIB-068 for this experiment, rely on PunchCard's task design to avoid large diffs.** Rejected: relying on the experiment's task design to avoid triggering a known gate defect is fragile — a single unexpectedly large agent-generated diff in the governed arm would silently invalidate that data point with no warning, and there's no way to confirm after the fact whether it happened without HIB-068's fix providing visibility.

- **B — Treat RISK-001 verification as optional, proceed with PunchCard and note it as a caveat in the writeup.** Rejected: RISK-001 is not a minor caveat — if session traceability is broken, the entire governed arm's outcome data becomes unreliable in a way that isn't a caveat, it's a validity failure. This needs to be resolved before, not disclosed after.

- **C — Pure option (a): route all oversized diffs into stratified review, regardless of size.** Rejected on review: stratified review (Component 3) was validated for the 400–5,000-line range. A diff tripping the *hard* ceiling could be substantially larger than that, and there's no evidence stratified review remains reliable at arbitrary scale — silently assuming it does risks trading one unreviewed-commit problem for a different one (an unreliable review masquerading as a real one).

- **D — Pure option (b): fail-closed-with-override for all oversized diffs, no stratified attempt.** Rejected on review: this discards review coverage entirely for diffs that a stratified pass could handle reasonably well (e.g. a 6,000-line diff with a small, well-defined high-risk subset), trading a fixable coverage gap for unnecessary friction.

- **E (chosen) — Hybrid: attempt stratified/thin-standard review first; fall back to fail-closed-with-override only when the reviewed subset itself exceeds a smaller sanity ceiling.** Preserves review coverage for the common case, avoids over-trusting stratified review at a scale it wasn't validated for, and gives both Scenario 1 and Scenario 2 a genuine, non-overlapping trigger condition rather than leaving one orphaned by an undecided implementation choice.

## 7. Known Residual Risks
- **Rebuttal cannot recover amend-fallback diffs** (v1.16, disclosed, not blocking): `rebuttal.py`'s manual `--rebuttal` invocation never sets `PRE_COMMIT_HOOK_STAGE=commit-msg`, so `get_staged_diff()`'s amend-recovery path (`ORIG_HEAD` detection, `HEAD~1..HEAD` fallback) was never reachable from a manual rebuttal even before this spec — a pre-existing limitation, not a regression introduced here. Fully solving this would require recording which diff-retrieval mode produced the original review's diff in the frozen artifact, out of scope for HIB-068.

- **Hash-migration transition window** (v1.13): moving `_get_normalized_diff_hash()` from diff-text hashing to a full-commit-state hash (`git write-tree`) means any `.agent/state/rebuttal_pass.json` token or frozen gate-findings artifact created before this change deploys will not match hashes computed after — an operational transition note, not a design flaw. Any in-flight rebuttal or pass token active at deploy time should be considered invalidated; no migration/fallback logic is planned for this narrow window given these are short-lived internal harness states, not durable data.
- **Rebuttal cross-file blindness for oversized commits** (v1.13): once `rebuttal.py` uses `get_scoped_diff()` for oversized commits, the rebuttal auditor sees only the same file subset the original review saw. A rebuttal that genuinely depends on context from an excluded file has no automated path to it — the developer must manually paste relevant content into the existing `evidence` field. This is the correct trade-off for the common case (consistency between what was reviewed and what's rebutted), not a bug, but a real limitation worth disclosing rather than silently discovering during PunchCard or general use.
- **Oversized-diff padding incentive** (corrected/narrower form of a reviewer finding): because `OVERSIZED_DIFF`'s override requires only a sentinel finding ID and an evidence string — no content-based judgment — while genuine stratified review evaluates real findings, there is a theoretical incentive to deliberately pad a commit past the hard ceiling (5,000 lines/200,000 chars) specifically to access the lower-friction override path instead of undergoing real review. Not fixed here — discouraging this fully would require content-aware padding detection (e.g. flagging suspiciously repetitive or low-information diff content), which is out of scope for this spec. Logged for awareness; worth revisiting if PunchCard or general usage surfaces this pattern in practice.
- The new sanity ceiling (`max_stratified_review_lines`, proposed default 2,000 lines, applied to whichever subset is actually reviewed) is a starting estimate, not empirically derived — it may need tuning once real oversized-diff cases are observed in practice (e.g. via PunchCard itself, or general project usage). Treat the default as provisional.
- Even with RISK-001 verified today, Antigravity itself could change between verification and the actual PunchCard run — the verification is a point-in-time check, not a permanent guarantee. Worth a quick re-check immediately before running if significant time elapses.
- The override mechanism (extending `SKIP_AI_REVIEW`) is inherently self-invokable by an autonomous agent, since it doesn't require interactive confirmation in every path (the env-var and file-based vectors don't). Scenario 3 makes agent-invoked overrides detectable after the fact, and Phase 4/Scenario 8 make checking for them a recorded commitment rather than an assumption — but detection is still the mitigation, not prevention. The override can still be used; the goal is that it cannot be used *silently*.
- **HIB-085** (tracked separately, not blocking this spec): this spec's Phase 0 deliberately gives `OVERSIZED_DIFF` strict stale-override-file rejection while the five pre-existing rebuttal types remain lenient (warn, don't reject). This asymmetry is a disclosed, deliberate trade-off — fixing it consistently across all six types is out of scope here and tracked as its own backlog item.
- This spec deliberately does not address D_task normalization or the logging plan — those remain real open items on the preflight checklist that need a decision before running, just not ones requiring harness code changes.
- The TOCTOU fix for `.skip-ai-reason.json` (§3, §8) closes a real code-level race, but its practical exploitability is lower than it might first appear: git already serializes commit operations per-repository via `.git/index.lock`, so two genuinely concurrent pre-commit hook executions against the same working tree require an atypical setup (e.g. multiple worktrees sharing state). Adopted regardless since the fix is cheap.
- The bounded/streaming read for `get_scoped_diff()` narrows but does not fully eliminate single-file memory risk — an extremely pathological case (e.g. a selected file whose diff content grows unpredictably during the streaming read due to a concurrent process) is not specifically hardened against here; the abort-on-threshold behavior is expected to be sufficient for realistic cases.
- **§8's `errors="replace"` requirement is not yet reflected as a dedicated Implementation Map row** (flagged 2026-08-01, pending Peter sign-off): the requirement is stated in §3 Assumptions prose (under "Size-first control flow (v1.16)") but the Implementation Map table's size-pre-check row does not separately call it out. Minor completeness gap, not a design defect — worth a one-line addition to the table before implementation begins.
- **`large_diff_fail_open` telemetry will drop to zero post-implementation** (flagged 2026-08-01): once the legacy hard-ceiling blocks (§3, §8) are deleted per this spec, no code path will ever emit a `large_diff_fail_open` event again — Scenario 4 only guarantees no *existing consumer* of that event type breaks, not that the event continues to fire. Anyone monitoring that metric's volume should expect it to go to zero once this spec ships, not treat that as a regression signal.

**Audit event naming** (standardized per review): `oversized_diff_stratified_reviewed` (diff > hard ceiling, reviewed subset within sanity ceiling, review completed on the sliced sub-diff), `oversized_diff_blocked` (reviewed subset exceeds sanity ceiling, no override, commit rejected), `oversized_diff_override_accepted` (reviewed subset exceeds sanity ceiling, valid fresh override present, commit proceeds — modeled on the existing `high_risk_gate_override` event pattern).

**Audit event payload schema** (all three `oversized_diff_*` event types): each event's `payload` field must include:
```json
{
  "original_lines": <int>,
  "original_chars": <int>,
  "sliced_lines": <int>,
  "sliced_chars": <int>,
  "strategy": "stratified | thin-standard",
  "vector": "tty | env | file",
  "rebuttal_type": "OVERSIZED_DIFF"
}
```
`vector` and `rebuttal_type` are only populated for `oversized_diff_override_accepted`. `vector` records which override mechanism fired (mechanically observable); it is not a proxy for agent-vs-human attribution — Phase 4's post-hoc analysis derives that separately by joining this event against `session_ledger.jsonl`. `oversized_diff_stratified_reviewed` and `oversized_diff_blocked` omit those two fields. This schema is what makes Scenario 3's agent-vs-human distinguishability and Phase 4's post-run `harness_events.jsonl` inspection actually queryable, rather than requiring free-text parsing.
